# Stagehand vs browser-use vs extension: Greenhouse

## Verdict (2026-09-29): Stagehand fixes the planner; it does not replace the extension

**Stagehand `extract()` is the planner browser-use failed to be.** On the same 5 postings:
85% field recall (browser-use 7%), 99% precision, median 17 s (vs 462 s), 2 LLM calls (vs 30),
~9k tokens (vs ~417k), on the same NIM model. It reads the page once and never clicks, so it
can't loop. The guard held on every run: canary blocked, 0 submits.

**Gaps that keep the extension in the loop:**
1. **Dropdown options: 13% (7/55).** React-select options aren't in the DOM until opened, and
   `extract()` never opens them. The extension still has to open each combobox at fill time.
2. **Consent/demographic tagging: 59% (16/27).** The Discord EEO block (10 fields) was skipped
   entirely. Harmless, because the extension never fills those, but a plan can't be trusted as
   the "never" list. Keep the extension's own regex rule.
3. **Required flag: 84%.** Keep the DOM `required`/asterisk check as ground truth, not the plan.
4. **NIM latency:** one 504 then a retry made Robinhood take 328 s. The slowness is the
   provider's, not Stagehand's (still 3 calls and ~11k tokens).

**Not compared:** the extension *fills* (71% of required fields filled or flagged); Stagehand
only *lists*. A plan helps only if the extension uses it to route fields (profile / answer bank
/ Review) before filling. That is the next test.

**Recommendation for ADR-016:** replace browser-use with Stagehand `extract()` as the
server-side, read-only planner (one call per job, shared across users). The extension still
fills and submits, opens dropdowns for their options, and keeps its own consent/EEO and
required checks. Measure Lever and Ashby next (about 1 min per posting instead of 8+).
